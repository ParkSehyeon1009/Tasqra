# AI 분석 v2 적용 안내

## 변경 내용

- AI 분류 출력은 RFP, PROPOSAL, COST_SHEET, CONTRACT, CONTRACT_CHANGE, REPORT, MEETING_NOTES, ETC의 8종이다. 세금계산서와 대가지급청구서는 ETC다.
- 응답 키 `category`, `reason`은 유지한다. 과거 한국어 6분류 이력과 사용자가 지정한 `documents.document_type`은 변경하지 않는다. 기존 BILLING 저장값도 유지한다.
- 모델 요청은 system 지시와 user JSON 데이터를 분리한다. OpenAI/로컬 모두 temperature=0을 사용하므로 이를 지원하는 모델이 필요하다.
- 요약·분류·개요에 문자열 타입, 길이, 코드 검증을 적용한다. 깨진 JSON을 정상 결과로 저장하지 않는다. 개요 실패는 산출물 표 생성을 막지 않는다.
- 짧은 문서 요약은 1회 호출한다. 긴 문서는 모든 구간에서 근거를 추출하고, 예산을 넘으면 기존 근거 ID를 선택해 줄인 뒤 최종 요약한다.
- 중간 단계에서 새 요약문을 반복 생성하지 않는다. 원문 인용이 해당 구간에 실제로 존재하는지 확인하고 원문 문자 위치를 서버에서 계산한다.
- 문단·줄·문장 경계를 우선하지만 큰 표/문장은 강제로 나뉠 수 있다. 주변 문맥을 겹치고 강제 분할 횟수를 결과에 표시한다.
- 분류는 요약 결과를 재사용하지 않는다. 긴 문서는 앞/중간/뒤 표본을 사용하고 생략 여부와 원문 범위를 표시한다.
- 실패한 호출만 설정 횟수만큼 재시도한다. 끝내 실패한 구간을 제외하고 완료 결과를 만들지 않는다.
- 토큰 사용량은 모든 호출을 합산한다. 응답을 받지 못한 호출이 있으면 전체 사용량은 알 수 없으므로 null로 기록한다.
- 최종 근거의 출처 검증은 의미 정확성 검증이 아니다. 모델이 원문을 잘못 해석하거나 중요 근거를 누락하는 가능성은 남는다. 실제 모델 평가가 필요하다.

## 실행 경로와 API 변경

```text
POST analyze → 작업 저장·큐 등록 → 202 응답
                               ↓
                      Celery documents.analyze
                               ↓
                 근거 추출 → 필요 시 근거 선택 → 요약·분류
                               ↓
                원문 버전 확인 → 결과와 COMPLETED 함께 커밋
```

`POST /api/projects/{project_id}/documents/{document_id}/analyze`는 이제 최종 결과가 아니라 작업 상태를 반환한다. 기존 직접 API 소비자도 변경해야 한다.

```json
{
  "job_id": "uuid",
  "document_id": 1,
  "status": "PENDING",
  "stage": "대기 중",
  "completed_units": 0,
  "total_units": 0,
  "error_code": null,
  "error_message": null,
  "analyses": []
}
```

- 상태 조회: `GET /api/projects/{project_id}/documents/{document_id}/analysis-jobs/{job_id}`
- 화면 재접속: 위 경로의 `{job_id}`를 `latest`로 조회한다. 작업이 없으면 null이다.
- 상태: PENDING, RUNNING, COMPLETED, FAILED. 완료 응답의 analyses에 최종 결과가 담긴다.
- 진행 건수는 **현재 단계** 기준이다. 전체 완료율로 해석하면 안 된다.
- 조회는 프로젝트 접근 권한, 실행은 프로젝트 편집 권한이 필요하다.
- 같은 문서·같은 분석 항목의 실행 중 작업은 재사용한다. 다른 분석 항목이면 409를 반환한다.
- 워커의 중복 전달은 중복 결과를 저장하지 않는다. 워커가 종료돼 중단된 작업은 전체 시간 제한 이후 조회/다음 실행에서 FAILED로 전환한다. 자동으로 이어서 실행하는 체크포인트 복구는 구현하지 않았다.
- 네트워크 문제로 화면 상태 조회가 실패해도 서버 작업은 계속될 수 있다. POST를 반복하기보다 latest를 다시 조회한다.
- 분석 중 원문 버전이 바뀌면 결과를 저장하지 않고 실패한다. 원문 버전은 OCR 전체 수정 횟수가 아닌 실제 텍스트 버전이다.

## 배포 순서

1. 기존 분석 요청을 마무리한 후 배포한다. API 응답 계약이 바뀌므로 프런트와 백엔드를 함께 배포한다.
2. 백엔드 작업 디렉터리에서 `alembic upgrade head`를 실행한다. 추가 리비전은 `20260831_0023`이며 analysis_jobs 테이블만 추가한다.
3. Redis/Celery 브로커가 가동 중인지 확인한다. API만 띄우면 분석이 대기 상태에 머문다.
4. 업데이트된 API와 Celery 워커를 재시작한다.
5. 로컬 단일 GPU에서는 워커 동시 실행 수를 우선 1로 시작하고 실제 처리량·메모리를 측정한다. 문서 하나 안의 요약·분류 및 구간 호출은 순차 실행하지만 여러 워커의 호출까지 전역 직렬화하지는 않는다.
6. 아래 컨텍스트 설정을 실제 모델 서버와 맞춘 뒤 테스트 문서로 검증한다.

## 설정

| 설정 | 기본값 | 의미 |
|---|---|---|
| AI_MAX_INPUT_CHARS | 6000 | 원문 한 구간 또는 분류 표본의 문자 상한 |
| AI_CONTEXT_TOKENS | 8192 | 실제 모델 서버의 컨텍스트 크기에 맞춰 입력할 값 |
| AI_MAX_OUTPUT_TOKENS | 1536 | 각 호출의 출력 예약·상한 |
| AI_CHUNK_OVERLAP_CHARS | 160 | 구간 사이 문맥 중첩 상한 |
| AI_MAX_CHUNKS | 256 | 문서 하나의 구간 수 상한. 초과 시 실패 |
| AI_CHUNK_RETRIES | 1 | 실패한 호출의 추가 재시도 수 |
| AI_TIMEOUT_SECONDS | 기존 설정 | 호출 하나의 시간 제한 |
| AI_ANALYSIS_TIMEOUT_SECONDS | 1800 | 큐 대기 포함 작업 전체 시간 제한 |

**AI_CONTEXT_TOKENS는 서버의 컨텍스트를 늘리는 설정이 아니다.** 서버가 2048인데 앱만 8192로 두면 안전하지 않다. 서버 컨텍스트를 동일하게 구성하거나 앱 설정을 실제 값으로 낮춰야 한다. 지시문과 출력 예약만으로 예산을 넘으면 오류로 중단한다.

모델 tokenizer를 추가로 메모리에 올리지 않기 위해 요청 JSON의 UTF-8 바이트 수를 보수적인 토큰 예산 대용으로 사용하고 메시지 여유 256을 더한다. 실제 모델 토큰 수를 측정한 값은 아니며, 안전성·처리량은 서버 tokenizer와 실측해야 한다. 기본 예산은 긴 한국어 문서를 더 작은 구간으로 나눌 수 있다.

구간 결과는 최대 6개 원문 인용으로 압축된다. 이것은 모든 문장을 읽는 방식이지 모든 사실을 보존하는 방식은 아니다. 전체 조항 추출·금액 감사 용도로 보장하지 않는다. 최종 통합까지 최대 8회 축약 단계를 허용하며 수렴하지 않으면 조용히 자르는 대신 실패한다.

## 검증 범위

단위 테스트는 메시지 역할, 원문 전체 범위 포함, 인용 검증, 분류 허용값, 길이·JSON 검증, 재시도, 단계별 통합 예산, 작업 중복·실패·시간 초과·원문 변경을 확인한다. 프런트는 빌드·변경 파일 린트로 검사한다.

실제 로컬 모델의 정확도·소요 시간, GPU 메모리, 실행 중 PostgreSQL/Redis/Celery를 통과하는 배포 검증은 별도로 수행해야 한다. 실제 서비스 DB에 이 작업에서 마이그레이션을 실행하지 않는다.

호출 파라미터 참고: [OpenAI Chat Completions 공식 문서](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).
